# ADR: PR-10a — authorizationdecide 接线 + auditquery permission-based 迁移

- Status: Accepted
- Date: 2026-06-12
- Issue: #1348 (EPIC #1337 PR-10, US4 / FR-014 / FR-015), Closes #914
- Scope: PR-10a delivery decisions only. The cross-layer authz threat model
  consolidation is owned by PR-13 (tasks.md T13.1); this ADR cross-references it.
  PR-10a wires the PDP + migrates the single #914 target (auditquery); the
  remaining business-endpoint sweep is PR-10b (see "Out of scope").

## Context

`authorizationdecide` (the ABAC PDP) implements `auth.Authorizer` but was never
injected into any route — dead code. Business endpoints authorized via in-token
role-literal comparison (`auth.AnyRole(auth.RoleAdmin)`). All PR-10 dependencies
(PR-5 #1343, PR-7 #1345, PR-8 #1346, PR-9 #1347, PR-11 #1349, PR-12 #1350) are
merged. PR-10a makes the PDP load-bearing on real route traffic and closes #914.

Two facts shaped the design:

1. **The engine is coarse (no per-endpoint target).** `Authorize(ctx, subject,
   resource, action)` evaluates *all* tenant policies by subject/env/resource
   conditions; `action` was observability-only and `resource` only fed the
   (empty mem) resource-attribute provider. `abac/condition.go` deliberately
   deferred action/resource-type targeting under YAGNI. PR-10 is the "real need".
2. **No seed/default policy exists.** An empty store → default-deny + forbid-wins
   → 403 for everyone including admins → would break every existing flow/test.

## Decisions

### D1 — Wire via composition-root → primary-listener context injection

The Authorizer lives in accesscore; auditcore/configcore cannot import it
(cross-cell). It flows the same way the Principal already does: the composition
root (`cmd/corebundle`) discovers the accesscore cell through a local
`authorizerProvider` interface (`Authorizer() auth.Authorizer`) — NOT a concrete
cell import (`corebundle-no-cells` depguard) — and passes
`bootstrap.WithPrimaryAuthorizer(...)`. Bootstrap installs a primary-listener-only
middleware that stamps the Authorizer into request ctx via the sole
`auth.WithAuthorizer`. The route Policy `auth.RequirePermission(p)` reads it back.

**Ordering subtlety (recorded because it is non-obvious):** the cell's
`Authorizer()` returns nil at `runtimeOptsFunc` time — the accesscore service is
constructed in `cell.Init` (bootstrap phase3), which runs *after* composition
`Build`. The composition root therefore injects a thin **lazy** Authorizer that
resolves the real service on first request (cached via `atomic.Pointer`) and
fails closed if the provider still yields nil. This keeps the
`WithPrimaryAuthorizer` nil-guard (phase0 fail-fast) honest while respecting the
construction order.

### D2 — Action-aware evaluator (`abac.Rule.Action`, additive)

`abac.Rule` gains an optional `Action []string`. EMPTY = untargeted (applies to
every action) — the natural default that preserves the evaluate-all semantics of
existing tenant-authored policies (they deserialize to nil Action, additive
omitempty, no PG/conformance break). `evaluate` threads the request action; a
rule is considered only when `len(Action)==0 || slices.Contains(Action, action)`,
then conditions AND-match. forbid-wins/default-deny unchanged; no new
`authz.Allow/Deny` call site (AUTHZ-DECISION-ALLOW-DENY-CALLER-01 intact — the
baseline is data). This realizes the first-class action target `condition.go`
deferred under YAGNI.

### D3 — Built-in baseline vs FR-011 fail-closed (security-model reconciliation)

A tenant-agnostic built-in baseline rule set reproduces the existing role gate:
`Effect=Allow, Action=["audit:read"], subject.role ∈ {admin, super-admin}`,
evaluated alongside tenant policies for every request. This is what keeps admins
working with an empty store and avoids per-tenant seeding.

**This does NOT violate FR-011 (fail-closed; never degrade to allow-all).** The
two govern different axes:

- **FR-011** governs *error/absence*: a missing attribute, an unreachable policy
  store, or a no-applicable-rule outcome → Deny. Unchanged.
- **The baseline** governs the *default policy set*: it is an action-scoped,
  role-conditioned **Allow rule**, exactly as narrow as the role gate it
  replaces — not a blanket allow-all.

**Tenant policies layer onto the baseline; they can add BOTH allows and denies
(F2, codex review).** An earlier draft of this ADR claimed a tenant policy "can
only tighten" the baseline. That is inaccurate: the shared PR-7 evaluator (the
general ABAC engine, also fed by policymanage PR-9 allow rules) treats a matching
tenant `EffectAllow` as a grant, so a tenant CAN widen the *route gate* beyond the
baseline (e.g. grant a non-admin `audit:read`). This is safe and intentional
because the route gate is NOT the data-visibility boundary:

- **Data visibility is governed independently by the principal-derived RowScope**
  (PR-5 `Principal.RowVisibility`), which a tenant policy cannot change. A tenant
  that grants a non-admin `audit:read` lets that caller PASS the coarse route gate,
  but the data layer still derives RowScope=self from the caller's identity and
  returns only their own rows. Tenant allow widens the *gate*, never *data access*.
- **forbid-wins still holds**: any matching tenant `EffectDeny` overrides every
  permit (XACML §7.16 / Cedar), so a tenant can also tighten.

The baseline is the policy-as-code expression of the role gate that was
previously hard-coded in handler Go — moving it behind the PDP, not weakening it.
Super-admin's cross-tenant RowScope=all remains PR-5's explicit audited path; the
route gate is a coarse allow/deny. It does not *enforce* obligations (RowScope/
FieldMask enforcement is PR-11/12, at the data-read PEPs), but it does **fail-closed
on a non-zero obligation** rather than silently drop it (F5, see §RequirePermission
godoc): an Allow that carries an obligation this gate cannot discharge is denied
until the data PEP lands. The baseline carries zero obligations, so the normal
path is unaffected.

**Threat-model note (re-evaluated for F2):** the security boundary for cross-actor
audit data is the principal-derived RowScope at the data layer, NOT the route-gate
permission. A tenant policy author (already trusted to manage their tenant's
policies) widening the route gate cannot exfiltrate another actor's rows, because
RowScope is identity-derived and policy-independent. The permission gate is
defense-in-depth on top of RowScope, not the sole control.

### D4 — Sealed `authz.Permission` + sealed Authorizer ctx funnel (Hard)

`auth.RequirePermission` takes a sealed `authz.Permission` (unexported field,
sole minter via the package registry; the closed set is exactly the exported
`Perm*` accessors). A role-name string literal cannot be passed where a Permission
is expected, so the #914 migration cannot regress into a role-literal gate. The
permission singletons are exposed as ACCESSOR FUNCTIONS (`PermAuditRead()`), not
exported vars (F6, codex review): an exported var was reassignable from outside
(`authz.PermAuditRead = Permission{}` could zero the global registry value), which
broke the "sealed value" claim; a function declaration is not reassignable, so the
registry value is now immutable by the type system (a reassignment is a compile
error — no runtime guard needed). The Authorizer travels through a private ctxkey
with a sole `WithAuthorizer` injector and sole `AuthorizerFromContext`/
`RequirePermission` reader. Both are Hard (string-typed concept funnel / sealed
construction), with stated upstream and downstream halves.

### D5 — Delete dead `RequireRole(authorizer,…)` scaffolding; retain deprecated helpers

The pre-existing `RequireRole(authorizer, …)` middleware + `handleRequireRole` +
`checkAuthorizer` were never wired (test-only). Rather than ship a second
PDP-consuming path beside `RequirePermission`, their fail-closed decision logic
is absorbed into `RequirePermission` and these three are **deleted**. The repo
has exactly one PDP route entry. (Pre-GA, no compat shim.)

**NOT deleted in PR-10a**: `RequireSelfOrRole` and `RequireAnyRole` are
**retained** (marked Deprecated) because they are still called by the eight
allowlisted cells in `PERMISSION-BASED-AUTHZ-01`. Deleting them in PR-10a would
break those callers; they are removed in PR-10b once the allowlist reaches zero.

### D6 — `PERMISSION-BASED-AUTHZ-01` is Medium, with a recorded Hard path

The archtest forbids `auth.AnyRole`/`auth.SelfOr`/`auth.RequireAnyRole` as an
authz gate in corecells business handlers, with an allowlist of the not-yet-
migrated slices (auditquery excluded → enforced now). It is **Medium**, honestly:
`auth.AnyRole` must remain callable by allowlisted cells until PR-10b, so the
violation cannot be made unrepresentable in PR-10a. Per the AI-robust charter, a
Medium with a low-cost Hard path must register an issue; the **Hard endgame** is:
declare the permission in `contract.yaml` → cellgen derives the `RequirePermission`
gate + golden (codegen-funnel Hard 范本, matching #914's "contract.yaml 声明权限
语义" and the eventbus metadata→cell_gen pattern), so a handler never hand-writes
the gate and a role literal is unrepresentable. Tracked for PR-10b/PR-13. The
allowlist is a migration ledger, shrunk to empty in PR-10b (SC-005 归零).

## Consequences

- The auditquery wire SHAPE is unchanged (request/response schema and the 200/403
  status set are all already declared) → no version bump.
- **F1 (codex review) tightens the empty-actorId case.** An empty `actorId` is no
  longer treated as an implicit self-read exempt from the PDP; it is a permissioned
  ledger read (for an admin it reads across every actor). Consequences:
  - An admin's empty-actorId (ledger-wide) read now goes through the PDP — closing
    the bypass where it skipped the gate entirely (a tenant forbid policy or an
    unwired PDP could not stop it before).
  - A non-admin's empty-actorId read now returns 403 (it lacks `audit:read`);
    a non-admin reads its OWN audit rows by naming itself (`actorId=<subject>`),
    which stays exempt. This is a behavior change (was 200 self-rows) accepted for
    a pre-GA security tightening; it stays within the already-declared 403 response,
    so no new contract version is minted (the wire shape and auth MODEL —
    "cross-actor reads require audit:read" — are unchanged; only the classification
    of empty-actorId is corrected). The 403 description is updated to name the
    permission deny (F7).
  - The route gate stays role-literal-free: it never inspects roles. Whether an
    admin/super-admin empty-actorId read is granted is decided by the PDP baseline.
- Existing auditquery handler tests now inject a ctx Authorizer (production-faithful;
  fail-closed otherwise); the migration's test debt is paid in the same PR.
- Production deployments get the admin baseline for free; tenant-specific
  policies layer on via policymanage (PR-9). No bootstrap policy seeding needed.

### Super-admin behavior: verified UNCHANGED (F15 / reviewer question)

A reviewer raised concern that the migration might change super-admin from HTTP
200 → HTTP 403 (or 501). **Verified: super-admin behavior at the route-gate
layer is unchanged.** The pre-migration gate was
`auth.AnyRole(auth.RoleAdmin, auth.RoleSuperAdmin)`, which granted both roles.
The built-in baseline in `baseline.go` reproduces exactly that set:
`Effect=Allow, Action=["audit:read"], subject.role ∈ {admin, super-admin}`.
So a super-admin principal continues to receive an Allow decision from the PDP
for `audit:read` — the route gate is unchanged.

The **501 Not Implemented** that super-admins receive comes from a different,
orthogonal path: `RowScopeAll` (which super-admins receive from
`p.RowVisibility`) is fail-closed in the data layer under per-tenant FORCE RLS
(#1618 — the NOBYPASSRLS serving role cannot enumerate tenants). This 501 was
present before PR-10a (introduced by #1618) and is unaffected by the PDP
wiring. The route gate for super-admin: before PR-10a = AnyRole allow → 200;
after PR-10a = baseline Allow → 200 — identical at the route layer. The 501
is the data layer rejecting RowScopeAll, not the PDP.

## Amendment: PR-10b — configcore migrated (#1348)

PR-10b applies the PR-10a mechanism (above) to the 5 configcore slices. No new
type machinery — it extends the closed Permission set and the built-in baseline,
then drains the migration allowlist. It does carry **one substantive decision**:
unlike auditquery, the configcore gates were admin-only, so routing them through
the shared `adminOrSuperAdmin()` baseline widens them to admit super-admin. That
relaxation is recorded explicitly below (PR pr-review F1 corrected an earlier
draft that mis-described it as "unchanged").

- **5 permissions minted** (`pkg/authz/permission.go`): `config:read` (configread),
  `config:write` (configwrite — folds create/update/delete), `config:publish`
  (configpublish), `flag:read` (featureflag — get/list/evaluate), `flag:write`
  (flagwrite). Same sealed shape as `PermAuditRead` (private singleton + accessor
  func; D4 Hard immutability holds). resource:action naming follows AWS-IAM /
  Spring-Security; the closed-registry test pins len 1→6 and each action string.
- **5 baseline rules** (`baseline.go`), one per permission, each gating the
  permission via the shared `adminOrSuperAdmin()` condition (Allow, action-scoped,
  subject.role ∈ {admin, super-admin}). D3's baseline≠downgrade and the forbid-wins
  / RowScope-independence arguments carry over verbatim.
  **Threat model re-evaluated — subject set WIDENED, not unchanged (PR pr-review F1):**
  unlike auditquery (whose pre-migration gate was already
  `auth.AnyRole(RoleAdmin, RoleSuperAdmin)` — see §"Super-admin behavior" above),
  the 5 configcore gates were `auth.AnyRole(RoleAdmin)` — **admin-only**, and
  `HasRole` is a literal membership check with no super-admin→admin inheritance
  (`runtime/auth/principal.go`). Routing them through `adminOrSuperAdmin()` therefore
  **widens** the config route gate to admit super-admin: a `superadmin`-only
  principal that the old literal gate denied (403) now passes (200). This is a
  deliberate, eyes-open **relaxation**, not an accident — super-admin ⊇ admin is the
  conventional administrative superset (Spring `RoleHierarchy`, Kubernetes
  `cluster-admin`, AWS-IAM/Cedar all model it, but only when *explicitly declared*,
  never as a silent side effect of a mechanism swap), and `adminOrSuperAdmin()` is
  the project's single declared admin-hierarchy condition, shared by audit and
  config. **Net effect today is zero**: `RoleSuperAdmin` has no production token
  issuer on develop (`runtime/auth/roles.go` — type-foundation constant only), so no
  live principal carries it. non-admins stay default-deny; a tenant `allow` can only
  widen the *route* gate, never data visibility (governed by principal-derived RowScope).
- **5 handlers migrated** to `auth.RequirePermission(authz.Perm*)`; configcore has
  no self/ownership branch (unlike auditquery) so no custom policy func is needed —
  a one-line policy swap per slice. The 14 configcore contract 403 descriptions name
  the permission deny and the admin + super-admin baseline grant (F7-consistency —
  the 403 texts already name super-admin, so they stay accurate under this ruling).
  **Ruling (api-versioning.md §"改变鉴权要求"):** no new contract version is minted.
  The mechanism swap (role literal → PDP) is not itself a wire change; the one
  observable delta is that a `superadmin` principal's route outcome moves **403→200**
  on the 5 config gates (admin → 200 and every non-admin/non-super-admin → 403
  ERR_AUTH_FORBIDDEN are unchanged; 403 is already declared in every contract.yaml).
  That delta is a **relaxation** — it grants access to a strictly-higher-privilege
  platform role, denies nothing previously allowed, and changes no field shape,
  status-code set, idempotency, or pagination. Under pre-GA (api-versioning.md
  §"兼容窗口": no Go API shim; wire contracts version only on *breaking* change),
  widening the admitted subject set to a not-yet-issued superset role is not a
  breaking wire change and needs no v1→v2 bump. (A *restriction*, a removed/renamed
  field, or changed status semantics WOULD require a new version.) This shares the
  *mechanism* of the PR-10a auditquery precedent but is NOT subject-set-identical to
  it: auditquery's pre-migration gate already admitted super-admin, so PR-10a changed
  no subject set, whereas configcore is a genuine relaxation — recorded here as an
  explicit, deliberate decision rather than an implicit side effect.
- **Assembly wiring already complete** from PR-10a F1: every root serving configcore
  (`cmd/corebundle`, `examples/ssobff`, `examples/corebundlestarter`) already calls
  `bootstrap.PrimaryAuthorizerOption`, so no new wiring — configcore endpoints hit
  the already-wired PDP.
- **Allowlist 8→3** (`PERMISSION-BASED-AUTHZ-01`): the 5 configcore entries removed,
  ceiling decremented to 3; the rule now fail-louds on any role-literal regression
  in configcore. e2e `TestABACPDPGatesConfigcore` (admin read/write→200,
  non-admin→403 PDP-deny) proves the wired PDP gates configcore on the real path.
- **Per-slice action-pin tests (test coverage, not a governance-tier enforcement
  mechanism)**: each configcore slice test asserts the gate asks the PDP for the
  *correct* permission string (the baseline allows admin for every config permission,
  so a wrong-permission misbinding would otherwise pass e2e and archtest silently).
  This is ordinary unit-test coverage — it does not qualify as a Medium/Hard archtest
  or governance rule under the ai-robust charter (which rates enforcement mechanisms
  such as type-aware scans, runtime guards, and codegen funnels, not test-level pins).
  The machine-grade Hard enforcement of the endpoint↔permission binding is PR-13
  (contract.yaml → cellgen-derived gate + golden).

## Amendment: PR-10c — accesscore migrated, allowlist drained to ∅ (#1348, closes EPIC PR-10 corecells sweep)

PR-10c migrates the 3 remaining accesscore slices (policymanage / identitymanage /
rbaccheck), draining the `PERMISSION-BASED-AUTHZ-01` allowlist to ∅ and closing
#1348. Unlike configcore, these carry `auth.SelfOr` ownership gates, so PR-10c adds
**one new code primitive** (the only new machinery): a self-exempt route gate.

- **New gate `auth.RequirePermissionOrSelf(pathParam, perm)`** (`runtime/auth/permission.go`):
  the migration target for `auth.SelfOr(pathParam, RoleAdmin)`. It permits the request
  when the path parameter equals the caller subject (self-access), and otherwise
  **delegates to `RequirePermission(perm)`**. This is NOT a second PDP path (D5's
  "exactly one PDP route entry" holds): the self branch is a *pre-PDP request-shape
  short-circuit* sanctioned by `tenancy.md §ABAC authz` ("self / ownership 检查…是请求
  形状判定…只有显式 `param == subject` 才豁免 PDP"); every non-self request flows
  through the sole `RequirePermission` gate. The `SelfOr` role-bypass branch becomes a
  permission gate; the self branch stays a request-shape exemption — it is deliberately
  NOT pushed into the PDP (see "Self/ownership in the PDP" below). Self-exemption is
  gated on `PrincipalUser` with a non-empty Subject (service/anonymous fall through to
  the PDP, fail-closed); empty or mismatched params fall through too ("空参数 ≠ self").
  **Superseded by the #1977 amendment below**: RequirePermissionOrSelf was deleted (no
  shim) and replaced by RequirePermissionForResource when self/ownership moved into the PDP.
  The shared `isSelfAccess(subject, target)` helper (canonical-UUID normalize both
  sides) is the **sole** self-comparison site, now used by both `RequireSelfOrRole`
  (legacy role-bypass) and `RequirePermissionOrSelf` (PDP-bypass) so the two cannot drift.
  **AI-robust grade: Medium** — the self-check is a runtime `param==subject` judgement,
  not type-expressible; it fails closed, and a non-vacuous unit test pins that a
  `param != subject` non-admin request is *denied* (an inverted self-check red-fails).
  Hard-ification rides the PR-13 codegen funnel with `RequirePermission`.
- **5 permissions minted** (`pkg/authz`): `policy:read`/`policy:write` (policymanage),
  `user:read`/`user:write` (identitymanage — "write" folds create/update/patch/delete/
  lock/unlock/change-password per the AWS-IAM Write access-level the prior uniform gate
  implied), `role:read` (rbaccheck). Same sealed shape as PR-10a/b (D4 Hard holds);
  closed-registry test pins len 6→11 + each action string + accessor self-discovery.
- **5 baseline rules** (`baseline.go`) via the shared `adminOrSuperAdmin()` condition.
  **Threat model re-evaluated — same super-admin WIDENING as PR-10b, not unchanged:**
  all 3 accesscore gates were admin-only (`auth.AnyRole(RoleAdmin)` /
  `auth.SelfOr("id", RoleAdmin)`; `HasRole` is a literal check, no hierarchy), so routing
  them through `adminOrSuperAdmin()` widens them to admit super-admin (403→200 for a
  superadmin-only principal). This is the identical deliberate relaxation ruled in the
  PR-10b amendment (super-admin ⊇ admin, explicitly declared via the project's single
  admin-hierarchy condition); **net effect today is zero** — `RoleSuperAdmin` has no
  production token issuer. The self branch of the SelfOr-migrated permissions
  (user:read/write, role:read) is **not** a baseline rule — it is the request-shape
  exemption in the gate, so the baseline only reproduces the admin (now admin/super-admin)
  path. Self-exemption does **not** widen data access: row visibility stays governed by
  principal-derived RowScope (D3 independence), and a forged path param cannot match a
  different subject (`isSelfAccess` compares canonical forms, empty never matches).
- **8 handlers migrated** across the 3 slices: admin-only gates → `RequirePermission`,
  self-or-admin gates → `RequirePermissionOrSelf`. Domain guards untouched (the
  self-deletion guard, S4.0 last-admin protection, the `authz.IdentityFieldMask()`
  projection on user-get / role-list/check — that field masking is PR-11/PR-12, orthogonal
  to the route gate). The 15 accesscore contract 403 descriptions now name the denied
  permission + the baseline grant (and, for the self-exempt endpoints, the self exemption);
  the last-admin / not-active / PUT-scope clauses are preserved verbatim.
- **Ruling (api-versioning.md):** no new contract version. Identical to the PR-10b ruling
  — the role→PDP mechanism swap is not a wire change; the only observable delta is a
  superadmin principal's 403→200 on the accesscore gates (a relaxation to a not-yet-issued
  higher-privilege role; admin→2xx and every other non-admin→403 unchanged; 403 already
  declared). The SelfOr→RequirePermissionOrSelf swap is subject-set-preserving for the
  self/admin paths (a user still self-accesses; an admin still passes), so it is wire-equivalent.
- **Assembly wiring already complete** from PR-10a F1 (`bootstrap.PrimaryAuthorizerOption`
  on every root serving accesscore). In-test assemblies that exercise the migrated gates as
  admin without the PDP were wired (same class as PR-10b's outbox-e2e fix:
  `cmd/corebundle` auth/setup integration harnesses + `tests/integration/l2atomicity`).
- **Allowlist 3→∅** (`PERMISSION-BASED-AUTHZ-01`): the 3 accesscore entries removed and the
  cheap exact-set-freeze ceiling test (`TestPermissionBasedAuthzAllowlist_Ceiling` +
  `expectedPermissionBasedAuthzAllowlist`) deleted with the last entry — an empty map cannot
  grow/swap silently and any re-addition is itself a reviewable diff. The rule is now a
  **zero-exception scan**: any role-literal gate in any corecells business handler is an
  unconditional violation (the SC-005 归零 end state). The reverse-fixture self-check remains
  the anti-vacuity. Hard-ification (codegen funnel + golden) is PR-13.
- **`TestAccessCore_ProductionAuthGateLock`** is the single authoritative endpoint↔permission
  action-pin (all 15 endpoints via the real routing path; 401 / 403-fail-closed / 403-PDP-deny
  / 2xx+wantAction, plus self-exemption for the 5 SelfOr-migrated endpoints) — consolidated
  there rather than duplicated per slice. e2e `TestABACPDPGatesAccesscore` proves the wired
  PDP on the real composition-root path, including a non-admin reading its OWN user/roles
  → 200 (self-exemption) and another's → 403 PDP-deny.
- **No shared accesscoretest authz helper**: unlike `configcoretest`, `accesscoretest` imports
  the accesscore cell (its hasher), so every internal accesscore test package would cycle
  through it — each slice + cell_test defines a local action-capturing Authorizer instead
  (verdict construction in `_test.go` per `AUTHZ-DECISION-ALLOW-DENY-CALLER-01`).

### Self/ownership in the PDP — deliberately deferred (true-ABAC carve-out)

> **Superseded by the "Amendment: #1977" section below.** This deferral was lifted: self/ownership
> is now a PDP decision (`subject.sub == resource.id` baseline rule via the `abac.OpEqualsAttr`
> cross-attribute operator). The paragraph below records the original PR-10c rationale; read the
> #1977 amendment for the current design + the re-evaluated threat model.

PR-10c keeps self/ownership as a request-shape gate exemption, not a PDP decision, per
`tenancy.md` + D3. A "more ABAC" alternative — modelling self-access as a
`subject == resource.owner` ownership *rule* in the baseline — is **not expressible today**:
the engine's `abac.Condition{Source,Key,Operator,Values}` supports only
attribute-vs-static-`Values` (no cross-attribute `subject == resource.owner` operator), and a
`SourceResource` owner attribute needs the PR-9 `ResourceAttributeProvider` (PIP); the route
gate currently passes only `resource = r.URL.Path`. Pushing self into the PDP would also
require amending `tenancy.md §self/ownership` + D3 (which currently forbid self in the route
PDP) and likely the `Authorizer.Authorize` signature — a separate architectural unit, not a
migration tail. Registered as a backlog follow-up (does not block #1348).

## Amendment: #1977 — self/ownership into the PDP (true-ABAC ownership rule)

#1977 **reverses the "Self/ownership in the PDP — deliberately deferred" carve-out above.**
Self/ownership is no longer a Go request-shape short-circuit; it is a first-class PDP decision —
the identity-ownership baseline rule `subject.sub == resource.id`. Driver: MDM (device management)
is starting, and devices are `owner ≠ id` resources that need a true cross-attribute ownership
primitive — so the operator has a real near-term consumer (not speculative).

**What landed (4 batches):**

- **Cross-attribute operator `abac.OpEqualsAttr`** (`internal/abac/operator.go`, wire `eq_attr`):
  the engine's first operator that compares the resolved `(Source, Key)` attribute against a SECOND
  resolved attribute `(RHSSource, RHSKey)` instead of static `Values`. `abac.Condition` gains typed
  `RHSSource`/`RHSKey` fields; `Condition.Validate`/`validateRHS` make the two shapes mutually
  exclusive (cross-attr ⇒ RHS set + empty Values; static ⇒ Values set + zero RHS) — an ill-formed
  mix is unexpressible (rejected 422). `matchCondition`'s RHS resolve is fail-closed on a not-found
  RHS (covered by `AUTHZ-EVAL-ATTR-NOTFOUND-GUARD-01`, which scans every resolve callsite).
- **`resource.id` identity attribute** (`authorizationdecide/attributes.go`): the resolver exposes
  the resource identifier (the value forwarded to `Authorize`) as `resource.id` — distinct from
  PIP-provided resource attributes, no DB lookup. Empty ⇒ found=false (fail-closed, preserves
  "空参数 ≠ self"). `Authorizer.Authorize`'s signature is **unchanged** (the original carve-out
  feared a signature change; it was avoided — the `resource` string already flows in).
- **3 baseline ownership rules** (`baseline.go`): `baseline-user-read-self` / `-user-write-self` /
  `-role-read-self`, each `Effect=Allow`, action-scoped to user:read / user:write / role:read, with
  the shared `subjectIsResource()` condition (`subject.sub OpEqualsAttr resource.id`). Together with
  the existing `adminOrSuperAdmin()` rules they reproduce the prior "self OR admin" — now both
  branches are PDP rules.
- **Owner-action grant-surface freeze** (`authorizationdecide/baseline_freeze_test.go`): the baseline
  grant surface of the owner-scoped actions (user:read, user:write, role:read) is frozen by
  `BASELINE-OWNER-RULE-TENANT-FREEZE-01` (Medium, value-golden over the unexported
  `builtinBaselineRules()`). It enforces two properties: (1) each owner self rule is `EffectAllow`,
  grants exactly its one action, and carries exactly the `subject.sub == resource.id` condition; (2)
  the set of allow rules granting each owner-scoped action is the closed `{owner, admin}` set —
  nothing else. Non-vacuity: a missing-self-rule check + a reverse-fixture table over property (1)
  + an injected separate tenant-allow rule that property (2) must reject. **Threat-matrix re-eval**
  (per `ai-robust.md`, an ADR amendment must re-assess the threat model): cross-tenant owner access is
  denied by the SAME ownership rule, because it compares request-local `subject.sub` vs `resource.id`
  and is **tenant-agnostic** — a tenant-B subject is denied exactly like a same-tenant non-owner, and
  tenant is **never** an owner-grant factor (tenant isolation is governed independently by the
  principal-derived `RowScope`/RLS). Because the PDP ORs allow rules and ANDs conditions within a
  rule, the real owner→tenant widening vectors the freeze closes are: **adding a SEPARATE
  tenant-matching allow rule** on an owner action (the primary vector — caught by property 2),
  replacing the owner condition with a tenant condition, or broadening an owner rule's Action (both
  caught by property 1). NOTE (PR #2075 review F2): adding an extra AND-condition to an owner rule
  does NOT widen — it tightens — though it is still rejected as forbidden drift; the widening always
  manifests as a separate allow rule or a replaced condition/action. The runtime behavior (wired
  server denies cross-tenant) is additionally covered end-to-end by `TestABACPDPGatesAccesscore`'s
  `cross_tenant_*` cases (#2026 / PR #2025 review F11).
- **`auth.RequirePermissionForResource(pathParam, perm)` replaces `auth.RequirePermissionOrSelf`**
  (`runtime/auth/permission.go`): it forwards the canonicalized (`httputil.ParseCanonicalUUID`)
  path-param value to the PDP as `resource`, enabling the ownership rule — it is **not** a self
  short-circuit (every request reaches the PDP). `RequirePermissionOrSelf` + its self-exemption are
  deleted (no shim). `isSelfAccess`/`RequireSelfOrRole`/`SelfOr` survive only for `examples/iotdevice`
  (PR-10d #1894); corecells cannot regress to a role-literal gate (`PERMISSION-BASED-AUTHZ-01`
  allowlist = ∅), and the owner-gate **shape** — must be `RequirePermissionForResource`, not plain
  `RequirePermission` (which forwards `r.URL.Path`, not the canonical resource id, silently breaking
  ownership) — is frozen by `OWNER-SCOPED-GATE-EXACT-SET-01` (Medium, exact-set typed scan over
  identitymanage/rbaccheck), closing the rules-only gap PR-10a's amendment left to `tenancy.md`
  alone (PR #2025 review F1).
- **Persistence + contract fanout**: PG codec (`policy_codec.go`) round-trips `eq_attr` + rhsSource/
  rhsKey (JSONB-additive, omitempty, **no migration**); the policymanage HTTP contract
  (`rule.schema.json` operator maxLength 6→7, optional rhsSource/rhsKey) regenerated + golden;
  `policymanage/converter.go` + the conformance suite carry the RHS through. The inbound RHS parse is
  single-sourced and **lossless** through `abac.ParseRHS` / `Condition.RHSWire` (shared by the HTTP
  converter and the PG codec): a half-formed `rhsKey`-without-`rhsSource` condition is preserved and
  rejected by domain `Condition.validateRHS` (the single structural authority) rather than silently
  dropped (PR #2025 review F2). `rule.schema.json` carries an `if/then/else` on `operator` that keeps
  the static-operator structure (`values` required + no RHS) — so a malformed static condition is
  rejected at the schema layer with **400**, restoring the pre-`eq_attr` status that briefly regressed
  to a domain 422 (PR #2025 review F3).

**Two ownership models (deliberate, so MDM is not an inconsistency):**

- **Identity ownership** (this PR): the resource *is* the principal (a user owns its own account /
  roles) → `subject.sub == resource.id`. `resource.id` is the request's own resource locator; no PIP.
- **Delegated ownership** (MDM, future): the resource has a *separate* owner (a device owned by a
  user) → `subject.sub == resource.owner`, where `resource.owner` is supplied by a device-cell PIP
  lookup. Same `OpEqualsAttr` operator, a different RHS key + a PIP — zero engine/contract change FOR
  THE ENGINE AND OPERATOR. However, MDM is NOT "fully unblocked with no work remaining": the device
  cell must still implement its own PIP (returning `resource.owner` for a given device resource),
  which may depend on the `resource_attributes` PG store (#1845). The cross-attribute operator
  machinery is ready; the device-cell PIP integration is a separate MDM deliverable.

**API-versioning ruling**: the policy wire change (#1977) is additive — the optional `eq_attr`
operator, optional `rhsSource`/`rhsKey` fields, and `values` becoming non-required are all
backward-compatible (existing policies using `eq`/`neq`/`in`/`not_in` remain valid; existing
API clients that do not send `rhsSource`/`rhsKey` are unaffected). No contract version bump is
required. Consistent with the PR-10a/b/c rulings: mechanism changes that are wire-equivalent or
strictly additive do not require a version bump.

**Availability note**: self-access now requires the wired PDP. Under a policy-store outage the
ownership rule returns 503 (the store-unavailable path in `Authorize` wraps the error as
`KindUnavailable`). Under the prior `RequirePermissionOrSelf` short-circuit, a self-access would
have succeeded with 200 even during a store outage. This is the intended fail-closed posture:
self-access goes through the same PDP as all other access, and a store outage surfaces as 503
rather than silently granting. Operators should account for this dependency in their SLO targets.

**Threat model re-evaluation (required by ai-robust.md; reconciles D3 + the lifted carve-out).**
Pushing self into the route PDP does **not** weaken the security model — it is additive
defense-in-depth on top of RowScope, the same posture the role baseline already had:

1. **RowScope remains the real data boundary (D3 independence, verbatim).** The ownership *route*
   allow only lets the owner pass the coarse gate; the data layer still derives `RowScope=self` from
   the principal (identity-derived, policy-independent) and returns only the owner's rows. An attacker
   who somehow passed the gate is still RowScope-bounded.
2. **`resource.id` provenance is trusted and unspoofable.** `resource.id` is the URL path target the
   client requested, canonicalized at the gate, compared to the JWT-fixed `subject.sub`. A client
   cannot make `subject.sub == resource.id` hold unless it *is* that subject (its JWT subject is fixed
   by authentication, not request-controlled). Empty / non-canonical / absent param ⇒ resource.id
   not-found ⇒ ownership rule cannot fire (fail-closed) — "空参数 ≠ self" preserved.
3. **forbid-wins still holds.** A tenant `Deny` rule overrides the ownership allow (deny-overrides).
4. **The ownership allow is action-scoped** (user:read/write, role:read) — it cannot leak to any
   other permission.

Net: the self check moved from Go (`isSelfAccess`) into the same PDP that already gates everything,
with identical end-to-end semantics (self OR admin). The one new operational dependency — self-access
now requires the wired PDP (mandatory in production via `bootstrap.PrimaryAuthorizerOption`; absent
Authorizer ⇒ 403 fail-closed) — is a strengthening, not a weakening.

**`tenancy.md §ABAC authz` amended in lockstep** (the self/ownership bullet): self/ownership is now a
PDP ABAC rule, not a handler request-shape judgement; the RowScope-independence and "空参数 ≠ self"
guarantees are restated and preserved.

## Amendment: PR-10d — examples migrated (iotdevice / todoorder, #1894)

PR-10d closes the "Out of scope" PR-10d bullet above: `examples/iotdevice` and `examples/todoorder` —
the last role-literal authz users in the repo — are migrated to permission-based gates, removing every
`auth.AnyRole`/`auth.SelfOr` route gate **and** the hand-rolled `authorizeCommandRole` gRPC role check
(iotdevice's only `principal.HasRole` literal). The helpers themselves are NOT deleted here (no callers
remain after this PR); deletion + the codegen Hard-ification stay PR-13.

**What landed:**

- **8 example permissions** in `framework/pkg/authz/permission.go` (the sealed registry is the SOLE
  minter, so example actions enroll alongside platform actions): iotdevice `device:command` /
  `device:consume` / `device:read` / `device:list`; todoorder `order:create` / `order:list` /
  `order:read` / `order:update`. Each is one orthogonal `(resource, read|write, coarse|ownership)`
  class — coarse and ownership actions are kept distinct so a coarse grant cannot bypass an ownership
  rule (the same closed-set discipline as the accesscore owner-action grant surface).
- **Example-owned PDPs**: each example cell ships a lightweight `Authorizer()`
  (`cells/devicecell/authorizer.go`, `cells/ordercell/authorizer.go`) wired via
  `bootstrap.PrimaryAuthorizerOption` — examples do NOT bundle accesscore and cannot import its
  `internal/abac` engine, so per "examples own PDP+baseline" each encodes its minimal baseline as a
  plain Go switch. iotdevice ownership is `subject == resource.id` (device-self); todoorder ownership
  is `subject == order.owner` (owner ≠ id, resolved by a PIP `repo.GetByID` lookup — `order.Owner` is
  a new server-derived field set from the JWT subject at create, off-wire). list / projection-summary
  stay coarse (`role:customer`); per-row owner filtering on list is a data-layer PEP (RowScope) tracked
  for PR-11/12, out of this route-gate migration's scope.
- **Two new `allowDenyCallerAllowlist` entries** (the Hard `AUTHZ-DECISION-ALLOW-DENY-CALLER-01` funnel):
  the two example `authorizer.go` files are the sole sanctioned `authz.Allow`/`authz.Deny` callers in
  their trees — exactly the "new sanctioned engine → add with rationale" case the funnel's godoc names.
- **`PERMISSION-BASED-AUTHZ-01` scan widened** from `./corecells/...` to `./corecells/... + ./examples/...`
  (workspace-scope `Typed` load, precedented by `fence_token_mint_funnel`). This is a **complementary
  Medium lock** that prevents the just-migrated examples from regressing to a role-literal gate; it is
  NOT the PR-13 Hard-ification (contract.yaml → cellgen + golden), which remains a separate mechanism.
  Rating unchanged (Medium): the helpers are still callable until PR-13, so the constraint is a typed
  scan, not a compile error.

**Threat-matrix re-eval** (per `ai-robust.md`, an enforcement change must re-assess the model):

- *Forging a verdict in an example* — the `authz.Decision` seal + the Hard caller-allowlist hold: only
  the two named `authorizer.go` files can construct Allow/Deny; any other example file referencing them
  is a CI failure (Production-scope workspace scan covers examples, confirmed by anti-vacuity).
- *Example route-gate regression to role-literal* — now Medium-guarded for the helper forms
  (`auth.AnyRole`/`SelfOr`/`RequireAnyRole`) by the widened scan. **Amendment (PR-10d review F3, this PR):**
  the residual hand-rolled `(*auth.Principal).HasRole` blind spot is now CLOSED — `PERMISSION-BASED-AUTHZ-01`
  grew a second, type-aware arm (`isPrincipalHasRoleCall`) that flags a `HasRole` authorization branch on a
  principal receiver in any non-allowlisted corecells/examples production file (separate
  `permissionBasedAuthzHasRoleAllowlist` records the three sanctioned uses — the two example PDP baselines +
  auditcore's RowScope/FR-007 derivation — each with a documented reason and a no-stale check; a RED
  fixture + GREEN non-Principal control prove fire-and-spare). Rating unchanged (Medium): the method stays
  callable, so the guard is a typed scan, not a compile error. **New, narrower residual blind spot**: a
  manual `for _, r := range p.Roles` membership check (corecells `identitymanage.callerHasRole`, a
  sanctioned field-level admin guard) is not the `HasRole` method and is not caught — flagging arbitrary
  range-over-`p.Roles` is a harder analysis left out of scope.
- *Cross-owner / cross-tenant access* — the example ownership rules are subject-vs-owner comparisons and
  therefore tenant-agnostic (same property as the accesscore #1977 ownership rule): a cross-owner subject
  is denied identically to a cross-tenant one; covered by the example authorizer + listener e2e tests
  (owner→200 / cross-owner→403 / no-authorizer→fail-closed 403).
- *No-principal at the gRPC edge* — now returns `ERR_AUTH_UNAUTHORIZED` (401) instead of the prior
  `authorizeCommandRole` 403, aligning the gRPC edge with the HTTP `enforcePermission` 401-before-403
  contract (a strengthening: authentication-vs-authorization distinction restored).

`tenancy.md §ABAC authz` and the `PERMISSION-BASED-AUTHZ-01` / `AUTHZ-DECISION-ALLOW-DENY-CALLER-01`
archtest godocs are amended in lockstep with this scope/allowlist change.
