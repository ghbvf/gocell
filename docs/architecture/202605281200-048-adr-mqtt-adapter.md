## 1. 背景

GoCell 消息层目前只有 RabbitMQ（AMQP 0-9-1）一个 broker adapter。MDM 推送通道、IoT 标准设备通道和零信任端点心跳均需要 MQTT。本 ADR 记录 adapters/mqtt 系列 PR 的关键决策，供后续 PR 审查与未来重构参考。

---

## 2. 决策记录

### 2.1 MQTT v5 only — 不提供 v3.1.1 兼容

**决策**：仅支持 MQTT v5，不引入 v3.1.1 兼容抽象层或双协议 seam。

**理由**：
- v5 新增 User Properties（`eventId` 幂等键传递）、Session Expiry Interval、Reason Codes（精确错误分类）、Flow Control。这些特性与 GoCell 的幂等/一致性/错误分类机制深度耦合；v3 缺少 User Properties，幂等键只能嵌 payload，需要额外协议层。
- v3 双协议抽象将增加约 25% 额外代码 + 测试矩阵翻倍，且 CI broker（Mosquitto 2.0）对 v5 的支持已完整。
- 业务方（IoT MDM）当前部署目标均支持 v5。

**影响**：调用方只能使用支持 v5 的 broker（Mosquitto 2.0+、EMQX 5.x、HiveMQ 4.x）。

### 2.2 客户端库：autopaho v0.23.0

**决策**：使用 `github.com/eclipse/paho.golang/autopaho` v0.23.0 作为唯一客户端库。

**理由**：
- autopaho 是 Eclipse Paho 官方 Go v5 客户端，内置 `ConnectionManager`（自动重连、会话恢复、backoff 注入接口），与 adapters/rabbitmq 自实现 reconnect goroutine 相比节省约 400 行代码。
- `ConnackError.ReasonCode` 提供 typed reason code 枚举，支持精确 bootstrap fail-fast / 瞬态 / 永久 三分类（见 §3 威胁矩阵 CONNACK 行）。
- `ReconnectBackoff` 注入点直接对接 `adapters/adapterutil.ExponentialBackoffWithJitter`（共享 helper），无需引入第三方 backoff 库。

**版本选择**：v0.23.0（2025 最新稳定版）相比 spec 草稿中的 v0.12 增加了 `AwaitConnection`、`WaitConnected` 等接口，更适合测试场景。

ref: `eclipse/paho.golang/autopaho/auto.go` — `NewConnection`, `ClientConfig`, `ReconnectBackoff`

### 2.3 DLT（Dead Letter）app-level 路由：`$dead/<topic>`

**决策**：Disposition.Reject 在 adapter 应用层 publish 到 `$dead/<originalTopic>`，不依赖 broker 特定 DLT 插件。

**理由**：
- MQTT v5 规范不含原生 DLT 机制；EMQX/HiveMQ 的 DLT 插件是非标准扩展，绑定特定 broker。
- app-level publish 到 `$dead/<topic>` 保持 broker 无关性，独立 subscriber 可以 subscribe `$dead/#` 做死信监控，topic hierarchy 与 GoCell outbox 语义一致。
- 与 adapters/rabbitmq 的 broker-native DLX 语义不同，此处是 adapter 负责路由；PR-4 实施。

### 2.4 clientId 唯一性：双 typed function（Ephemeral / Stable）+ sealed ClientID

**决策**：clientId 格式 `{cellID}-{role}-{instanceID}`，封装在 sealed struct `ClientID` 中。提供两个 typed function（typed function choice Hard 范本）：

- `ParseEphemeralClientID(cellID, role string)` — 内部生成 uuid 作为 instanceID。`SessionExpiry == 0`（clean session）时使用，避免节点重启 session 残留。
- `ParseStableClientID(cellID, role, instanceID string)` — caller 提供稳定的 instanceID（pod name / node ID 等）。`SessionExpiry > 0`（persistent session）时使用，broker 凭 stable ClientID 恢复未确认消息。

构造器集合内部全部委托私有 `assembleClientID` 完成 `ClientID{value: value}` 字面量构造——`MQTT-CLIENT-ID-NAMESPACE-01/A2` 的 allowedFuncs 集合 = `{assembleClientID}`，是包内唯一合法构造点。

**理由**：
- 单一 `ParseClientID` 强制内嵌 uuid 锁死了持久会话语义（C6 round-1 finding F10）。typed function choice 让"选错语义 = 选错 API 名"在 caller 命名空间编译期可见，符合 ai-robust.md「typed function choice」Hard 范本。
- MQTT broker 会对 clientId 重复的新连接强制断开旧连接。ephemeral path 用 uuid 后缀避免 k8s 滚动更新场景的踢人；stable path 用 caller-supplied identity 服务持久会话。
- cellID+role 前缀保留了可读性，便于 broker 侧 ACL 配置（基于 clientId 前缀的 Topic ACL）。
- 格式约束（lowercase segment regex + length ≤ 128）由 `validateCellRole` / `validateInstance` / `assembleClientID` 在构造期强制。

### 2.5 sealed-struct funnels vs string-newtype（ClientID / TopicNamespace）

**决策**：ClientID 和 TopicNamespace 均使用 `struct{ value string }` sealed struct，而非 `type X string` string newtype。

**理由（为何 sealed struct 优于 string newtype）**：

| 属性 | `type X string` | `struct{ value string }` |
|------|----------------|--------------------------|
| 包外 literal 构造 | `X("raw")` 合法 | 编译期错误（unexported field） |
| AI-robust 上游 Hard | 仅 archtest | Go 编译器 |
| 类型转换绕过 | `X(s)` 合法 | 编译期错误（no underlying string） |
| 零值语义 | `X("")` 合法 | `X{}` 合法（.value == ""，String() 返回 ""） |

sealed struct 的上游 Hard 来自 Go 可见性规则：包外无法构造 unexported 字段的 struct literal。string newtype 在包外可以通过 `ClientID(rawString)` 类型转换绕过，必须依赖 archtest（Medium 上游）拦截。

参照：`pkg/errcode.PublicDetail` sealed-value pattern（同源设计，DETAILS-SEALED-FIELD-FROZEN-01）。

### 2.6 backoff 提升到 adapterutil 共享 helper

**决策**：指数退避 + jitter 逻辑提取到 `adapters/adapterutil/backoff.go`，rabbitmq adapter 同步重构使用同一实现。

**理由**：
- adapters/rabbitmq 原有 `rabbitmq/backoff.go` 与本 adapter 需要的逻辑完全相同。
- 单源治理（DRY），避免 backoff 参数语义在两个 adapter 间悄悄漂移。

### 2.7 PUBACK 错误映射（PR-2 落地）

**决策**：`classifyPubackReason` 将 MQTT v5 PUBACK reason code 映射到独立的 `errcode.Code` + `errcode.Kind`，以及 `PublishFailureReason` metric label，三者保持 1:1 对应。

**控制流（关键）**：paho 对 PUBACK **reason code ≥ 0x80** 走 **error 通道**返回 `(resp, err)`（`resp.ReasonCode` 已设，`err` 非 nil；见 `paho/client.go:923`），**不是**经 nil-error 的 `resp` 返回。因此 `< 0x80`（0x00 / 0x10）走 `Publisher.Publish` 成功分支，`≥ 0x80` 走 `err != nil` 分支由 `handlePublishError` 处理——后者**必须**先用 `resp.ReasonCode` 驱动 `classifyPubackReason`，再回落到 transport/ctx 兜底。早期实现把 `err != nil` 直接 `wrapPublishErr`，导致下表 0x80/0x83/0x87/0x90/0x97/0x99 全部塌缩成 generic `ErrAdapterMQTTPublishFailed`——`classifyPubackReason` 对这些 code 实为死代码。该路径由 `TestPublisher_Publish_BrokerRejectedPUBACK_RealPath`（真实 broker 返回 ≥0x80 reason，断言专属 errcode）守护防复发。

**完整映射表**（ref: MQTT v5.0 spec §3.4.2.1）：

| PUBACK 0x__ | 规范名称 | errcode.Code | errcode.Kind | Disposition 语义 | metric reason |
|-------------|---------|--------------|--------------|----------------|---------------|
| 0x00 | Success | — (Ack path) | — | outbox.Ack | — (success path) |
| 0x10 | NoMatchingSubscribers | `ErrAdapterMQTTPublishNoSubscribers` | `KindUnavailable` | Ack + slog.Warn（broker 接受但无 subscriber，视为成功）| — (success path) |
| 0x80 | UnspecifiedError | `ErrAdapterMQTTPublishRejected` | `KindInternal` | outbox.Reject | `rejected` |
| 0x83 | ImplementationSpecificError | `ErrAdapterMQTTPublishRejected` | `KindInternal` | outbox.Reject | `rejected` |
| 0x87 | NotAuthorized | `ErrAdapterMQTTPublishNotAuthorized` | **`KindUnavailable`** | **outbox.Requeue** | `not_authorized` |
| 0x90 | TopicNameInvalid | `ErrAdapterMQTTPublishRejected` | `KindInvalid` | outbox.Reject | `rejected` |
| 0x97 | QuotaExceeded | `ErrAdapterMQTTPublishRateLimited` | `KindUnavailable` | outbox.Requeue | `rate_limited` |
| 0x99 | PayloadFormatInvalid | `ErrAdapterMQTTPublishPayloadFormatInvalid` | **`KindInvalid`** | outbox.Reject | `payload_format_invalid` |
| default | (未知代码) | `ErrAdapterMQTTPublishRejected` | `KindInternal` | outbox.Reject | `rejected` |

**关键决策理由**：

**0x87 NotAuthorized → KindUnavailable（retryable）**：PUBACK 0x87 与 CONNACK 0x87 对齐——CONNACK 侧已归为 `classPermanentRetain`（readyz 503 + autopaho 继续重连等待 operator 修复）。PUBACK 侧同理：ACL 配置错误是 operator 可修复的运维问题，条件在 operator 修复 broker ACL 后自然消失。将其设为 retryable 使 outbox relay 在修复期间持续重试（受 retry budget 约束，耗尽后走 DLX），而非当作永久客户端错误直接丢弃消息。此语义与 `ErrAdapterMQTTPublishRejected`（KindInternal，永久）的区别在于：Rejected 代表消息本身不可接受（格式/路由错误），NotAuthorized 代表操作权限不足（外部条件）。

**0x99 PayloadFormatInvalid → 独立错误码 `ErrAdapterMQTTPublishPayloadFormatInvalid`（KindInvalid）**：payload 格式问题与 payload 尺寸问题（`ErrAdapterMQTTPayloadTooLarge`，0x95 broker 侧拒绝）是不同失败域：format 是内容编码错误，size 是物理限制。复用同一错误码会混淆告警维度（format invalid 应检查 payload 编码逻辑；too large 应检查 MaximumPacketSize 配置），故引入独立码。两者均为 KindInvalid + Reject，语义一致。

**`never_connected` reason 从 metric 删除**：`mqtt_publish_failed_total` 的 `reason` label 原计划含 `never_connected`，但 `Connection.Publish` 不做 phase 检查——pre-connect 阶段的 publish 调用经 autopaho 内部排队，等连接建立后发送，不会被 publisher 侧以 `NeverConnected` 错误拒绝；失败表现为 `puback_timeout` 或 `context_canceled`。该 label 在 publisher 路径结构上永不 emit，故删除以保持闭集完整性。`ErrAdapterMQTTNeverConnected` 错误码保留供 Health probe / WaitConnected 超时路径使用。

**metric `reason` 闭集**（PR-2 落地后完整集合，共 10 个）：
`payload_too_large`, `closed`, `puback_timeout`, `context_canceled`, `publish_error`, `topic_outside_namespace`, `rate_limited`, `not_authorized`, `payload_format_invalid`, `rejected`

### 2.8 NewPublisher 构造函数签名：`(*Publisher, error)` vs `*Publisher` + panic

**决策**：`NewPublisher` 返回 `(*Publisher, error)`，而非 `*Publisher` + 内部 panic（不对齐 `adapters/rabbitmq.NewPublisher`）。

**参数分类与处理方式**：

| 参数 | 分类 | 错误处理 |
|------|------|---------|
| `clk clock.Clock` | 程序员错误（编译期忘传，位置参）| `clock.MustHaveClock(clk, ...)` panic（B 类，同 rabbitmq） |
| `conn *Connection` | 运行时值（依赖注入，可为 nil）| 返回 `error`（结构化诊断）|
| `ns TopicNamespace` | 运行时值（依赖注入，可为零值）| 返回 `error`（结构化诊断）|

**理由**：
- `nil clock` 是 programmer error：调用方在编译期已知类型，漏传是代码缺陷；panic 与 `clock.MustHaveClock` 统一语义（CLOCK-POSITIONAL-INJECTION-01），与 rabbitmq 一致。
- `nil Connection` / 零值 `TopicNamespace` 是 caller 在 runtime 传入的依赖值（来自 DI 容器、配置解析、环境变量），失败原因是 wiring 配置错误，不是 programmer error。bootstrap wiring 路径需要结构化错误（errcode.Error with Details）来产生可观测的诊断日志，而 panic 会阻断 wiring 流程并产生不友好的 stack trace。
- 此决策使 `NewPublisher` 与 GoCell 中 `NewService` 系列构造函数的模式一致（required dep → validateRequired() → returned error），只是 clock 参数因其 programmer-error 语义保留 panic。

ref: `adapters/rabbitmq/publisher.go` — `NewPublisher(*Publisher)` + `clock.MustHaveClock`；对比见 PR-2 `adapters/mqtt/publisher.go` 签名注释。

### 2.9 onServerDisconnect 使用 disconnectReasonName（PR-2 落地）

**决策**：`onServerDisconnect` callback 调用 `disconnectReasonName`（MQTT v5 §3.14.2.1 DISCONNECT reason code 表），而非 `connackReasonName`（§3.2.2.2 CONNACK 表）。

**理由**：CONNACK 与 DISCONNECT 两个包虽有若干数值重叠，但每个 code 在不同包类型下的含义不同（例如 0x87 在 CONNACK 表示"连接未授权"，在 DISCONNECT 表示"会话被踢"，语义相关但上下文不同）。统一用一张表会产生 slog 日志中的 reason_name 字段与 broker 实际语义不符的问题，导致运维混淆。三张独立表（connackReasonNames / pubackReasonNames / disconnectReasonNames）分别锁定各自 spec 章节，互不复用。

## Amendment 2026-05-29 — PR-3 Subscriber

PR-3 adds the MQTT **receive path**: shared-subscription SUBSCRIBE, the
received-PUBLISH dispatch loop, QoS1 manual acknowledgement, and the
EventBus-Disposition mapping. This amendment documents the design and re-evaluates
the security posture. Where this amendment contradicts pre-PR-3 prose, the
amendment is authoritative and the original text is rewritten in place (no two
truth sources) per `.claude/rules/gocell/ai-robust.md` §"ADR amendment 落地必查".

### Shared-subscription mapping: `$share/{ConsumerGroup}/{filter}`

GoCell maps the EventBus two-axis consumer model onto MQTT v5 shared
subscriptions (§4.8.2):

- **ConsumerGroup axis (competing consumers)** → the `$share/{group}/` wire
  prefix. All subscribers that mint a filter with the same `consumerGroup` join
  one broker-side share group; the broker load-balances each matching PUBLISH to
  exactly one member. This is the MQTT equivalent of an AMQP/Kafka consumer
  group: same group = competing consumption.
- **filter axis (topic selection)** → the bare `filter`, validated against the
  namespace. The broker strips the `$share/{group}/` prefix from delivered
  PUBLISH packets, so the delivered topic is **group-blind** — the adapter does
  NOT re-match it client-side. Instead each route carries an **MQTT v5
  Subscription Identifier** in its SUBSCRIBE packet; the broker echoes that
  identifier on every delivered PUBLISH, and `onPublishReceived` routes the
  delivery to the single route whose sub-id matches. This is what lets two
  *different* consumer groups subscribe the *same* topic on one connection
  without cross-group fanout (each group is a distinct shared subscription with
  its own sub-id; a bare-topic match cannot tell them apart). See **§Amendment
  2026-05-30 (F1)** — this supersedes the original PR-3 design that carried a
  client-side `matchFilter` and fanned a delivery out to every topic-matching
  route.

`TopicNamespace.MintFilter(consumerGroup, filter)` is the sole constructor of the
sealed `subscribableFilter{wireFilter}` token (the SUBSCRIBE wire form only;
client-side topic matching was removed when dispatch moved to sub-ids). It
rejects an empty `consumerGroup` (a shared subscription requires a group) and
validates `filter` against the namespace via `SubscribeOK`. Verified against
**mochi-mqtt v2.7.9** (embedded broker used in integration tests) and
**mosquitto 2.0** — both honor `$share/{group}/{filter}` competing-consumer
semantics, lowercase `$share`, and echo Subscription Identifiers on delivery.

### QoS1 Disposition mapping (no broker NACK)

MQTT has **no NACK**: a receiver either PUBACKs a QoS1 message or leaves it
unacked. The three EventBus dispositions map onto this as follows. `EnableManualAcknowledgment`
is set on the paho `ClientConfig`, so the broker does not auto-PUBACK; the
subscriber controls settlement explicitly via `(*Connection).ack`.

| Disposition | MQTT action | Settlement |
|-------------|-------------|------------|
| **Ack** (success) | Commit idempotency claim, **then** PUBACK | `(*Connection).ack(pb)` after Commit |
| **Requeue** (degraded-state) | Leave the message **unacked**; the broker redelivers on session resume / reconnect. This is the **accepted Option C behavior** (ADR-050 §6): the adapter sees Requeue only in degraded states (shutdown/backend-down/contention) where leave-unacked is correct; `SupportsRequeue=false` declared. | Release the claim (no PUBACK) |
| **Reject** (permanent) | Error-slog + **PUBACK-as-poison** (PUBACK to stop infinite redelivery); Release the claim | `$dead/<originalTopic>` publish *before* the PUBACK so the poison payload is captured for ops (PR-4 #1142, via `MintDeadLetter`) |

Ordering is a correctness invariant for **Ack**: the idempotency claim MUST be
committed before the PUBACK, so a crash between Commit and PUBACK results in a
redelivery that the Claimer dedupes (at-least-once → effectively-once), never a
silent drop.

**Requeue head-of-line limitation — resolved by Option C (ADR-050 Accepted)**:
paho's manual-ack tracker (`acksTracker.flush`) flushes PUBACKs to the broker
**strictly in receive order, stopping at the first un-acked packet**, and MQTT
QoS1 redelivers only on session resume / reconnect (spec §4.4). A single
leave-unacked Requeue would theoretically block all later PUBACKs and stall intake
after `Receive Maximum` deliveries. This limitation is **moot under Option C**:
`ConsumerBase` is the sole retry layer — it retries transient handler failures
in-process and converts them to `DispositionReject` (ProcessReason="retry_exhausted")
before the adapter sees them. Consequently, the adapter receives `DispositionRequeue`
**only in degraded states**: graceful shutdown (ctx cancel), fail-closed idempotency
backend, or claim contention. In all these states the system is non-steady and
leave-unacked-then-redeliver-on-reconnect is the intended behavior. HoL stall cannot
accumulate in steady state because no business `Requeue` ever reaches the adapter.
See ADR-050 §6 for the full decision rationale.

### Manual ack via `*paho.Client` / `mqttAcker`

autopaho v0.23.0's `*ConnectionManager` does **not** expose an `Ack` method
(verified against the vendored module). Manual acknowledgement therefore routes
through the package-unexported interface:

```go
type mqttAcker interface { Ack(pb *paho.Publish) error }
```

`onPublishReceived` captures the delivering `pr.Client` (a `*paho.Client`, which
implements `mqttAcker`) into the unexported `Connection.ackClient` field under
`subMu`. `(*Connection).ack` is the sole callsite of `acker.Ack` — locked by
`MQTT-ACK-CALLSITE-FUNNEL-01` (below). The subscriber calls `conn.ack(...)` (the
wrapper), never `acker.Ack` directly, and never the concrete `*paho.Client.Ack`.

### Session recovery + clientId-conflict takeover

- **Session recovery**: `CleanStartOnInitialConnection = (SessionExpiry == 0)`.
  When `SessionExpiry > 0` (clean=false) with a **stable clientId**, the broker
  retains the session (subscriptions + unacked QoS1 messages) across reconnects,
  so unacked Requeue'd messages are redelivered on resume. autopaho does not
  replay SUBSCRIBE packets itself, so `onConnectionUp → resubscribeAll → sendSubscribe`
  re-arms every route after a reconnect (idempotent; runs as a no-op on the first
  Up because no routes are registered yet).
- **clientId-conflict takeover**: MQTT brokers enforce clientId uniqueness — a
  second CONNECT with the same clientId causes the broker to DISCONNECT the
  earlier session with reason `0x8E` (Session Taken Over). `onServerDisconnect`
  decodes and slog-Warns this via the DISCONNECT reason-code table (NOT the
  CONNACK table). Stable clientIds are an operator-configuration concern; two
  instances sharing a clientId will fight (mutual takeover loop). The
  `ClientID` sealed type (`{cellID}-{role}-{uuid}`) makes accidental collisions
  unlikely; operators MUST NOT configure two instances with identical stable
  clientIds.

### `$share` offline redelivery is NOT a durability guarantee — the outbox is

A clarification refining the "session recovery" bullet above. Whether the broker
offline-queues messages for a `$share/{group}/{filter}` member that is temporarily
disconnected (`SessionExpiry > 0`, stable clientId) and redelivers them on resume
is **environment- and timing-dependent, and therefore NOT relied upon**:

- Locally (`eclipse-mosquitto:2.0.22`), a `$share` member that dropped its
  connection **uncleanly** (Open-ctx cancel / TCP teardown, not a clean
  DISCONNECT) *did* have all 3 absence-published QoS1 messages offline-queued and
  redelivered on resume (`offline-redelivered=3/3`).
- The **same code on CI** (same pinned image) redelivered **zero**
  (`offline=0`) — the PR-3 CI failure that first exposed this.

The divergence is inherent: offline-queueing for a share member hinges on a race
between the broker observing the disconnect as *non-clean* and retaining the share
session, versus the offline publish arriving — and a graceful `(*Connection).Close`
deliberately `unsubscribeAll`s first (clearing the share subscription), yielding
nothing queued. None of these is a contract `$share` promises.

**Consequently the GoCell consumer-group path does NOT depend on broker offline
queues for durability.** At-least-once delivery is provided by the producer-side
transactional outbox (retry until an online consumer acks) + QoS1 + idempotent
consumers (two-phase Claim/Commit/Release). This is a deliberate **semantic
divergence from the rabbitmq EventBus**, where a durable per-group queue retains
messages for offline consumers: *rabbitmq consumer-group = durable-offline; mqtt
consumer-group = online-load-balance, durability via the outbox.*

`TestIntegration_Subscriber_SessionRecovery` therefore hard-asserts only the
DETERMINISTIC invariant — the persistent session resumes, the `$share`
subscription re-arms, and a message published while the resumed member is **online**
is delivered — and records offline-redelivery counts as observability only (not an
assertion). The phase-1 teardown still uses an unclean Open-ctx cancel (not
`Close`) so the session is genuinely retained and resumed; that is what makes the
online-delivery-after-resume assertion exercise real session recovery.

> **Plan §3.4 reconciliation.** The criterion "clean=false 离线消息补投
> integration 验证" as literally stated (broker offline-queue redelivery on the
> consumer-group path) is not a deterministic guarantee of `$share` and is not
> CI-assertable. The achievable, asserted equivalent is persistent-session
> *resume* + online delivery resumption; cross-restart durability for the
> consumer-group path is the outbox's responsibility, exercised by the
> outbox/producer test suites rather than here.

**Operational note:** a graceful GoCell shutdown via `Connection.Close` cleanly
*retires* a subscriber (it unsubscribes the broker-side subscription). It is NOT a
"pause that retains offline messages" — and even an unclean drop's offline
retention is best-effort per the above, so operators must rely on the outbox for
durability across consumer downtime, not on broker offline queues.

## Amendment 2026-05-30 — PR-3 review fixes (F1/F4/F7/F8/F10/F11/F12)

Adversarial review of PR-3 surfaced correctness, contract, and observability
defects in the newly-landed Subscriber. This amendment records the resolutions
and re-evaluates the §3 / §"PR-3 receive-path threat review" matrices. Each is a

### F1 — dispatch by Subscription Identifier (supersedes `matchFilter` fanout)

**Defect**: `onPublishReceived` matched each delivered PUBLISH against every
route's bare `matchFilter` and dispatched to *all* matches. Two subscriptions on
the same topic with different consumer groups (`$share/A/t` vs `$share/B/t`) have
identical `matchFilter`, so one delivery fanned out to both groups' handlers —
double processing + double-ack of the same `*paho.Publish`. Registration was
group-aware (`wireFilter`) while dispatch was group-blind.

**Resolution**: each route is assigned a monotonic **MQTT v5 Subscription
Identifier** (`Connection.subIDSeq`, ≥1) set on its SUBSCRIBE
(`SubscribeProperties.SubscriptionIdentifier`); `resubscribeAll` reuses the
route's stable sub-id across reconnects. `onPublishReceived` reads
`pb.Properties.SubscriptionIdentifier` and dispatches to the single matching
route. The client-side topic matcher (`topicFilterMatches`) and the
`subscribableFilter.matchFilter` field are **deleted** — the broker already
matched the topic; the sub-id says which subscription it matched.

**Broker requirement (fail-closed)**: a broker that returns SUBACK `0xA1`
(Subscription Identifiers Not Supported) now fails Subscribe fast with the new
`ErrAdapterMQTTSubscriptionIDsUnsupported` code. A delivered PUBLISH with no
sub-id (broker protocol violation, impossible after a successful SUBACK) is
logged at Error and dropped (left unacked) — never guessed onto a route. Both
mochi-mqtt v2.7.9 and mosquitto 2.0 support Subscription Identifiers. Single
sub-id per delivery is sufficient: GoCell uses only shared subscriptions, which
the broker delivers separately per group (multiple sub-ids per delivery only
arise for overlapping non-shared subscriptions, which GoCell never creates).

### F4 — call `outbox.NotifySettlement` on every settlement branch

**Defect**: the Subscriber never called `outbox.NotifySettlement`, so
`SettlementObservers` attached to a `HandleResult` (by `kernel/wrapper`,
observability middleware) were silently dropped on the MQTT consume path —
unlike `adapters/rabbitmq` (10 call sites) and `runtime/eventbus` (6).

**Resolution**: `NotifySettlement` is now called on every branch of
`dispatchDisposition`/`dispatchAck` (Ack success / commit-failed→Requeue /
ack-failed; Reject success / poison-ack-failed; Requeue; unknown→Requeue),
mirroring the rabbitmq mapping. Enforced by new archtest
**`OUTBOX-SUBSCRIBER-SETTLEMENT-NOTIFY-01`** (Medium: every exported
`outbox.Subscriber` impl package must call `outbox.NotifySettlement`) +
white-box `TestSubscriber_NotifySettlement_FiresObservers`. The broker-backed
cross-impl conformance (`outboxtest.TestPubSub` asserting observer firing)
remains PR-4 scope (the settlement path is not reachable cross-package without a
live broker); the enrollment waiver is updated accordingly.

### F7 — UNSUBSCRIBE on a cancellation-detached ctx

**Defect**: the `Subscribe` cancel-closure called `cm.Unsubscribe(ctx, …)` with
the subscription ctx, which is already canceled by the time Close/StopIntake run
it → UNSUBSCRIBE failed immediately with context-canceled. **Resolution**: use
`context.WithoutCancel(ctx)` (preserves request-scoped values, drops
cancellation; autopaho `PacketTimeout` bounds it — same rationale as
`resubscribeAll`).

### F8 — resubscribe-after-reconnect failure surfaced in `Health`

**Defect**: `onConnectionUp` advanced to `phaseConnected` then re-armed routes;
a failed re-SUBSCRIBE only logged + metered, while `Health` still returned `nil`
→ readyz green while the broker had no subscription (silent receive stall).
**Resolution**: `Connection.lastResubscribeErr` (under `c.mu`) is set by
`resubscribeAll` on the first failure and cleared on a fully-successful pass;
`Health` returns it while `phaseConnected`.

### F10 — QoS 2 rejected fail-closed at construction

`NewSubscriber` now rejects `QoS > 1` (`ErrAdapterMQTTInvalidConfig`) before
`setDefaults`, instead of silently SUBSCRIBE-ing at QoS 2 (which breaks the
manual-ack at-least-once idempotency model).

### F11 — auth-code reasonName redaction unified across CONNACK/SUBACK/PUBACK

**Defect**: only CONNACK moved the human-readable `reasonName` to the Internal
channel for auth-related codes; **SUBACK** (`subackError`) and **PUBACK**
(`handlePublishError`) leaked `reasonName` (incl. `0x87 NotAuthorized`) in Public
details. **Resolution**: a single funnel `reasonDetailOptions(reasonCode,
reasonName, isAuth)` (in `errors.go`) makes the auth-redaction decision once;
CONNACK/SUBACK/PUBACK all route through it. New archtest
**`REASON-NAME-REDACTION-01`** (Medium) bans `errcode.PublicString("reasonName",
…)` outside that funnel. (These errors are all 5xx-classified, so Public details
are stripped from the wire today regardless; the fix is defensive consistency +
removes the latent leak should a code ever be reclassified to 4xx.)

### F12 — dedicated `ErrAdapterMQTTAck`

`(*Connection).ack` no longer reuses `ErrAdapterMQTTSubscribe` for ack failures
(no-delivering-client / manual-ack-failed); it returns the new
`ErrAdapterMQTTAck` (`KindUnavailable`) so operators can route ack-path failures
independently from SUBSCRIBE failures.

### Round-2 review fixes (#2 / #3 / #6)

A second review pass surfaced deeper consume-path issues outside the original
F1–F16 frame:

- **#3 — bounded concurrent dispatch (fixed)**: paho calls `OnPublishReceived`
  synchronously on a single inbound-dispatch goroutine (`routePublishPackets`),
  so the original synchronous `processDelivery` meant one slow handler stalled
  intake for the whole connection. `makeReceive` now hands each delivery to a
  bounded worker pool (`SubscriberConfig.MaxConcurrentHandlers`, default 16;
  `workerSem` semaphore) and spawns a per-delivery goroutine; the existing
  `inflight` poll-drain already covers goroutine drain. Saturation blocks the
  callback as intended back-pressure (keep the bound ≤ Receive Maximum). Guarded
  by `TestSubscriber_ConcurrentDispatch_SlowHandlerDoesNotBlock`. Note: this does
  **not** address the HoL issue (#2) — concurrency is about *running* handlers,
  the HoL block is about *un-acked* messages; #2 is resolved by Option C (ADR-050 §6).

- **#2 — Requeue head-of-line limitation (resolved by Option C, ADR-050 §6)**:
  the original ADR framed Requeue/leave-unacked as benign "Receive Maximum
  back-pressure". That was wrong: paho's `acksTracker` flushes PUBACKs strictly
  in receive order (breaks at the first un-acked), and MQTT redelivers only on
  reconnect, so **one** Requeue would block all later PUBACKs and stall intake
  within `Receive Maximum` deliveries. The misleading paragraphs (§QoS1 Disposition
  mapping caveat, §3 matrix, receive-path threat review) are rewritten above;
  the design decision is Option C (ADR-050 Accepted, PR-4 #1142): ConsumerBase is
  the sole retry layer and the adapter sees Requeue only in degraded states
  (shutdown/backend-down/contention) where leave-unacked is the correct behavior.
  `SupportsRequeue=false` declared. HoL stall cannot accumulate in steady state.

- **#6 — minor hardening (fixed)**: (a) `MintFilter` empty-consumer-group error
  now carries `filter` on the Internal channel (not Public details), consistent
  with `SubscribeOK`; (b) the unmarshal-poison path now wraps the decode error
  with `ErrAdapterMQTTUnmarshalEnvelope` (previously a declared-but-unused code)
  so poison is grep-able by a stable code in slog.

Matrix additions (no regressions):

| Threat | Status | Mitigation / compensation |
|--------|--------|---------------------------|
| **Slow-handler intake stall** (sync handler blocks paho's single inbound-dispatch goroutine) | ✅ fixed (#3) | Bounded worker-pool dispatch (`MaxConcurrentHandlers`); slow handler bounds, never stalls, intake. |
| **Requeue head-of-line stall** (single leave-unacked Requeue blocks all later PUBACKs, reconnect-only recovery) | ✅ resolved (Option C, ADR-050 §6) | Limitation is moot under Option C: ConsumerBase is the sole retry layer; adapter receives Requeue only in degraded states (shutdown/backend-down/contention) where leave-unacked is the correct behavior. ## Amendment 2026-06-02 — #1356 DLT no-loss policy（决策定稿 + 机器强制 + no-loss 重定位）

### 触发

#1356（P1, label `no-loss`）要求 "$dead publish 失败时消息绝不能丢"。本 amendment **不改变** §2.3 / §3 line-193 的 fail-closed-and-drop 决策——它**强化**该决策（加机器强制 + OSS 证据），并诚实定性"字面 no-loss 在 transport 层不可达"，把 no-loss 保证重定位到正确的架构高度。

### 结论:no-loss 的本质是持久化底座,MQTT app-level `$dead` 没有

跨 OSS 框架核实"DLQ 发布本身失败"的处理（不是 Requeue 语义，是 sink-publish-failure 这个具体场景）：

| 框架 | DLQ-publish 失败时的行为 | 能否移植到 MQTT app-level `$dead` |
|------|------------------------|------------------------------|
| Kafka Connect `DeadLetterQueueReporter`（KIP-298） | producer 客户端内置 `retries`/`delivery.timeout.ms` 吸收瞬态 → 仍失败则 log + `deadletterqueue-produce-failures` 指标 + **drop** | 部分：drop+metric 即 GoCell 现状；paho 缺 producer 那层内置持久重试 |
| Spring Kafka `DeadLetterPublishingRecoverer` | DLT publish 失败 → **不提交 offset → seek 重读**（no-loss） | ❌：MQTT 无 offset 重读模型；等价物 = leave-unacked = 复活 Option C 的 paho 按序-PUBACK HoL stall（ADR-050 §1） |
| Watermill `PoisonQueue`（Go） | poison-topic publish 失败 → `errors.Join` 返回 → router `Nack` → **重投**（no-loss） | ❌：Watermill 无官方 MQTT PubSub；其 `Nack=干净重投`假设在 MQTT 上 = leave-unacked = HoL |
| autopaho（GoCell 所用库）官方 no-loss 配方 | 持久化 `ClientConfig.Queue` + 文件级 session store（磁盘底座） | 需引入磁盘持久化底座；评估见 §持久化 store |

**共同点**：每个达成 no-loss 的框架都依赖**持久化底座（Kafka log / 磁盘 queue）或干净重投底座（offset 重读 / clean Nack）**。MQTT app-level `$dead` 两者都没有：它是非持久化传输，且 paho 严格按序 PUBACK 使 leave-unacked 必然 HoL（ADR-050 §1）。因此 **adapter 层不是放 no-loss 保证的正确位置**——这与 ADR-050 Option C 对 Requeue 的判断完全同构。

来源：[Watermill poison.go](https://github.com/ThreeDotsLabs/watermill/blob/master/message/router/middleware/poison.go) · [autopaho pkg.go.dev](https://pkg.go.dev/github.com/eclipse/paho.golang/autopaho) · [Kafka Connect DLQ — Confluent](https://www.confluent.io/blog/kafka-connect-deep-dive-error-handling-dead-letter-queues/) · [Spring Kafka error handling](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)

### 决策

1. **adapter 契约定稿** = fail-closed-drop + alertable 信号。`routeDeadLetter` 在 mint 失败 / broker publish error / broker PUBACK reason ≥ 0x80（paho 经 error 通道透传，见 §2.7 / publisher.go:158-187）三类失败上 log-Error + `mqtt_dlx_failed_total{cell,reason}` + ack-as-poison。**不** leave-unacked（HoL）。
2. **alertable 信号机器强制**：新增 archtest `MQTT-DLX-FAILURE-SIGNAL-FUNNEL-01`（Medium）——`routeDeadLetter` 每个 `return`（drop 退出）必须前置 `RecordDeadLetterFailure`（失败信号);成功指标 `RecordDeadLetter` **不**满足该断言（把 drop 记为 success = 带假成功计数的静默丢失）。使"静默 drop / 误记成功"在结构上不可表达。这是把原本的 Soft 文档约定升为可强制契约。符号清单 + 盲区自检 + Hard 升级路径活在该 archtest 的 package godoc。
   > **运行时发射前提**：该指标仅在消费侧 wire 了 provider-backed `SubscriberCollector` 后发射;`mqtt.NewSubscriber` 默认 `NoopSubscriberCollector{}`(不发射),且当前 develop 无生产 MQTT subscriber 装配。archtest 守的是"代码里必有该调用"(静态),指标实际可见性依赖装配——wiring guard 随第一个 MQTT-consuming cell 落地(#1435)。在那之前死信失败可观测性为 0(transport 已在 develop 无消费方,无实际丢失面)。
3. **no-loss 重定位（deferred）**：字面 no-loss（"绝不丢"）需要持久化底座。GoCell 的持久化底座是**消费 cell 的本地事务**——消费 cell 在永久失败时应在本地 tx 落一条持久 dead-letter 行再 `Reject`（即 Spring offset 重读 / Watermill clean-Nack 在 GoCell 的等价物），或桥接到 AMQP/Kafka（ADR-050 Option C 同款建议）。当前 develop **无 MQTT-consuming cell**（iotdevice 为 publish-only），故无 enforcement 对象；该 enforcement 在真实消费 cell 出现时落地，登记于 backlog **#1435**（带机制，不写投机指南——Soft 严禁立项，见 ai-robust.md）。
   > **面向未来 MQTT-consuming cell 开发者**：MQTT adapter **不**提供与 AMQP broker-native DLX 等同的 no-loss 保证。消费 MQTT 的 cell 若需 no-loss，**必须**在本地事务里落 dead-letter 记录再 `Reject`——否则 poison 消息在 `$dead` 失败路径上会被 fail-closed 丢弃（仅 `mqtt_dlx_failed_total` 告警可见）。这不是 adapter bug，是 transport 层的结构性边界。
4. **有界进程内重试**：deferred（#1334，数据驱动，无 OSS 传输层先例）。
5. **archtest Hard 化**：`MQTT-DLX-FAILURE-SIGNAL-FUNNEL-01` 从 Medium 升 Hard（drop 决策收口为 typed sink helper）deferred（#1440）。

### §3 威胁矩阵逐行重评（ai-robust「ADR amendment 落地必查」）

- line 193（`$dead` publish 本身失败）：**✅ → ✅**（未回退）。状态从"已接受取舍 + 告警"强化为"已接受取舍 + 告警 + **机器强制信号不可静默** + no-loss 重定位声明"。无 ✅→⚠️/❌ 格子；无补偿缺口。
- 其余行：本 amendment 不触及，状态不变。

### 持久化 store（评估，deferred）

autopaho 的 no-loss 配方（持久化 `ClientConfig.Queue` + 文件 session store）对 GoCell **疑似冗余**：出站重启丢失已由 outbox relay（DB 重发）覆盖；入站未 ack 重启已由 broker 侧 `SessionExpiryInterval` + 稳定 clientId 重投覆盖；QoS2 本地去重态不适用（GoCell 用 QoS1 + idempotency Claimer）。是否引入文件 store 作数据驱动评估，登记 backlog **#1434**，不投机实现。

## Amendment 2026-06-03 — #1247 token sealed-construction（package-internal Medium → Hard）

**背景**：publish/subscribe token（`publishableTopic` / `subscribableFilter`）的构造 allowlist（A2/A2b/A3 + S3）此前评为 **upstream 包内 Medium**——adapters/mqtt 包内可写 `publishableTopic{topic: x}` 字面量绕过 `PublishOK`，仅靠 archtest 拦截。#1247 跟踪把该轴升 Hard。

**issue 原提议机制不成立**：#1247 原提议引入 marker interface `type publishGate interface{ publishGate() }`。经核实该机制**关不住** composite-literal 轴——marker interface 只阻止包外实现，不阻止包内 `publishableTopic{...}` 字面量构造（字段对 adapters/mqtt 仍可见）；若让 `Connection.Publish` 改收 interface 反而**放宽** funnel（允许包内多实现）。external 轴本就 Hard，marker 在该轴零增益。

**落地机制（sealed construction via internal/）**：token 类型 + 校验 + 构造器整体迁入 `adapters/mqtt/internal/topicns/`：
- `TopicNamespace`→`topicns.Namespace`，`publishableTopic`→`topicns.PublishableTopic`，`subscribableFilter`→`topicns.SubscribableFilter`（**字段仍 unexported**），`ParseTopicNamespace`→`topicns.Parse`；4 个 topic-validation 错误码同迁（避免 `adapters/mqtt → internal/topicns → adapters/mqtt` 循环 import），`errors.go` 以 `const = topicns.Err*` 重导出。
- `adapters/mqtt` 以 `type TopicNamespace = topicns.Namespace` **type alias** 重导出（零成本，非 facade 层），public API + `examples/iotdevice` 不变（仅消费 namespace `.String()` + `NewPublisher`，从不碰 token）。
- 因 token 字段在 `topicns` 内 unexported，adapters/mqtt 内 `topicns.PublishableTopic{topic: …}` = **编译错误**（`cannot refer to unexported field topic in struct literal`，实测反向自检）。

**威胁矩阵逐行重评（无 ✅→⚠️/❌ 回退，本 amendment 是 Medium→Hard 改善）**：

| 轴 | 旧评级 | 新评级 |
|----|--------|--------|
| token 构造 in adapters/mqtt | Medium（archtest A2/A2b/A3 + S3） | **Hard**（type-system 跨包 unexported 字段，compile error） |
| token 构造 in internal/topicns | — | Medium（Mint 必与 token 同包的真 ceiling；A2/A2b/A3 + S3 rescope 到 `topicnsPkgPath`） |
| token 构造 package-external | Hard | Hard（不变） |
| downstream cm.Publish/Subscribe/Ack callsite | Hard | Hard（不变） |

与 #851（SPAN holder seal）/ #893（HEALTHZ holder seal）的本质差异：那两者是 **holder 轴**（Go 无法表达「谁可声明某类型的字段」）的真 ceiling，故 won't-do；#1247 是 **construction 轴**，可由 internal/ 跨包字段封闭——故是「可关闭的延后」而非「不可达 ceiling」，本 amendment 关闭之。残留（Mint 与 token 同包的 internal/topicns 包内字面量）是 construction 轴在单包内的真 ceiling，surface 极小（~1 文件）。

**残留 benign 项（不立 archtest，刻意）**：adapters/mqtt 仍可构造**零值** `topicns.PublishableTopic{}`（无字段可设）→ 空 topic；不携带攻击者可选 topic，且空 topic 被 broker 拒（MQTT v5 §4.7.3）。为一个 broker 已拒的 benign 退化态立 archtest 违反 ai-robust ≥Medium 立项门槛 + 优雅简洁，故文档化而非 enforce。

**反向自检 rescope（防静默 vacuous）**：`MQTT-TOPIC-NAMESPACE-01` 的 A1 field-freeze 经 alias 透明解析 `topicns.Namespace`（不变）；A2 construction-allowlist + B1 `reflect.New` blind-spot rescope 到 `internal/topicns`/`Namespace`（否则 namespace 构造轴随迁移静默 vacuous，已加非真空实证：在 internal/topicns 植入 `Namespace{value:…}` outside Parse → A2 红）。

**单源**：完整 sub-rule 清单 + 评级活在 `tools/archtest/mqtt_callsite_funnel_test.go` package godoc；本节只记决策。
