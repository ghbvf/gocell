# ADR: 共享 error schema 单源 + codegen mirror funnel（#677）

- 日期：2026-05-25
- 状态：Accepted
- 关联：issue #677（本变更）、ADR `docs/architecture/202605031600-adr-v1-schema-evolution.md` §5（error envelope 例外，本 ADR 完成其后续收敛）、ADR `docs/architecture/202605241700-adr-contracts-shared-cas-mixin-funnel.md`（同命名空间 CAS mixin 参照对象）
- archtest：`SHARED-SCHEMA-MIRROR-FUNNEL-01`（`tools/archtest/shared_schema_mirror_test.go`）
- verify gate：`gocell verify codegen-shared-schema`（in-process 字节 diff）

## Context

`contracts/shared/errors/error-response-v1.schema.json` 是框架 error envelope 的 wire schema。在 #677 之前，该 schema 以**4 份实体文件**形式存在：

| 路径 | 角色 |
|------|------|
| `contracts/shared/errors/error-response-v1.schema.json` | 主仓库 canonical |
| `examples/iotdevice/contracts/shared/errors/error-response-v1.schema.json` | iotdevice example 副本 |
| `examples/todoorder/contracts/shared/errors/error-response-v1.schema.json` | todoorder example 副本 |
| `tests/contracttest/testdata/contracts/shared/errors/error-response-v1.schema.json` | contracttest fixture 副本 |

PR #396 引入了 `TestSharedErrorSchema_CopiesInSync`（`bytes.Equal` 比对 3 个副本与主 canonical），它只是**检查**而非物理收敛——4 份文件仍是独立实体，任何一份被人工编辑都会导致其余副本静默漂移至下次 CI 运行才被发现。这是 AI-robust **Soft** 形态：字节比对的 test 无法阻止 AI 直接写副本文件。

## Decision

把 error envelope schema 收敛为**单一手写源 + codegen 派生 3 mirror**：

- **canonical 源**：`contracts/shared/errors/error-response-v1.schema.json`（唯一允许手工编辑的副本）
- **mirror 清单**：`tools/codegen/sharedschema` 包的 `Mirrors` 变量（`map[canonicalRel][]destRoot`）声明 3 个派生目标：`examples/iotdevice`、`examples/todoorder`、`tests/contracttest/testdata`
- **生成命令**：`gocell generate shared-schema` → 调用 `sharedschema.Generate(root, dryRun)`，把 canonical 字节恒等写到 3 个目标路径
- **verify gate**：`gocell verify codegen-shared-schema` → 调用 `sharedschema.Verify(root)`，in-process 字节 diff，任一 mirror 漂移或缺失均返回非零退出码，由 CI `verify-codegen` job 守护
- **删除旧测试**：`TestSharedErrorSchema_CopiesInSync` 删除，verify gate 取代其功能且强制物理同步
- **reverse-enum archtest**（`SHARED-SCHEMA-MIRROR-FUNNEL-01` A1）：在 CI 全量扫描 repo，发现任何不在 `sharedschema.Mirrors` 声明集内的 `error-response-v1.schema.json` 副本即报错——新增 mirror 必须先进 `Mirrors` 清单
- **caller-allowlist archtest**（`SHARED-SCHEMA-MIRROR-FUNNEL-01` A2）：`codegen.WriteOptions{Headerless: true}` 复合字面量只允许出现在 `tools/codegen/sharedschema` 包，其他包使用即 CI 红

### 为何 JSON 走 `codegen.Write{Headerless: true}` 而非普通 `codegen.Write`

`codegen.Write` 的安全卫士在写入前检查目标文件首字节是否匹配 `governance.IsGoCellGenerated`（要求 `// Code generated by gocell` 前缀），以防意外覆盖用户手写文件。JSON 文件首字节是 `{`，结构上无法携带 `//` 行注释，因此无法满足该前缀约束。若不绕过该门，`codegen.Write` 在第一次写入后的每次 regenerate 时都会拒绝覆盖自己产生的文件。

为此在 `WriteOptions` 新增 `Headerless bool` 字段：`true` 时跳过"必须是 generated file"的前置检查，允许写入/覆盖不含 generated header 的文件。`Headerless` 是一个逃生口，用 archtest A2 caller-allowlist 把它锁在 `tools/codegen/sharedschema` 包——只有 sharedschema 包可以声明 `Headerless: true`，其他包使用即视为绕过 funnel，CI 拒绝合并。

## 与 CAS mixin ADR 的正面对比（L3 概念一致性）

CAS mixin ADR（`202605241700`）和本 ADR 同在 `contracts/shared/` 命名空间，但采用了**不同的单源治理范式**，原因如下：

### CAS mixin 选择「`$ref` 物理单份」

`contracts/shared/cas/v1/expected_version.schema.json` 的 6 个消费方（4 个 body schema + 2 个 DELETE query param）全部位于**主仓库同一 `contractsRoot`** 下，`$ref` 的相对路径解析路径完全可达。codegen DTO parse（`contractgen/jsonschema.go::fillRef`）和 runtime embed bundler（`refbundle.go`）都在主仓库树内运行，可以安全跟随 `$ref`。物理上只有 1 份定义，`$ref` 让消费方引用它——**违反在物理层不可表达**（Hard）。

### Error envelope 选择「codegen 派生物理 3 份」

Error envelope 的 3 个消费方落在 **3 个独立 `contractsRoot`**（`examples/iotdevice/contracts/`、`examples/todoorder/contracts/`、`tests/contracttest/testdata/contracts/`），无法通过 `$ref` 到主仓库根：

**物理 reader 1**（`tests/contracttest/contracttest.go` 第 385-423 行，`compileSchemaFile`）：

```
pathWithinAllowList(t, cleanDir, fullPath)
  → findContractsRoot(cleanDir) 查找最近上层 "contracts" 目录
  → 只允许 <nearestContractsRoot>/shared/ 以下路径
  → 超出此范围的 $ref 路径 → t.Fatalf("escapes allow-list")
```

`compileSchemaFile` 在 symlink 解析后检查路径前缀（`contracttest.go:431-450`），fail-closed：若 `error-response-v1.schema.json` 以 `$ref` 指向 `../../../../../../contracts/shared/errors/error-response-v1.schema.json`（逃出 example 的 `contracts/` root），`findContractsRoot` 只找到 example 下的 `contracts/`，解析后路径不在 `<exampleContractsRoot>/shared/` 下，test 失败。

**物理 reader 2**（`tools/codegen/contractgen/builder.go:119-120`）：

```go
reqPath := filepath.Join(rootDir, contractDir, contract.SchemaRefs.Request)
schemaBytes, err := os.ReadFile(reqPath)
```

这是相对路径 `os.ReadFile`，`rootDir` 是契约所在 example 的根目录，`contract.SchemaRefs.Request` 是相对于 contractDir 的路径。如果 example 的 `request.schema.json` 里写了 `$ref` 到仓库主根，展平的路径会超出 example 根，`os.ReadFile` 返回 not-found 错误，codegen 构建失败。即使 `$ref` 是相对路径如 `../../../../contracts/shared/errors/error-response-v1.schema.json`，打开后这是 contractgen embed bundler 路径（`bundleSchemaRefs`），它的 `IsWithinRoot` 守护是相对于 contractgen 的 rootDir（example 根），路径逃出即拒绝。

**结论**：两个 reader 的 allow-list 结构都是「以自身 contractsRoot 为 root，`shared/` 是 root 内的特殊路径」。主仓库 canonical 对于 example 的 contractsRoot 是「外部」，`$ref` 跨 root 的路径会被两个 reader 各自拒绝。因此**照搬 CAS 的物理单份 + `$ref` 引用是不可行的**——无法在两个 reader allowlist 限制下解析到主仓库 canonical。唯一可行的治理路径是在每个消费 contractsRoot 下保留物理副本，并用 codegen funnel 确保字节恒等。

### `contracts/shared/` 命名空间语义无冲突

CAS ADR（`202605241700` §Out of scope）明确 `contracts/shared/` 是「mixin-only 命名空间（跨 kind 共享 schema 片段）」。这是对**主仓库内**跨 kind 共享的描述：shared schema 片段不是契约本体（http/event/command/projection），而是被多个契约 `$ref` 引用的 mixin。

本 ADR 讨论的是**跨 contractsRoot 的副本治理**——不同 contractsRoot 下各自存在物理副本是必需的（见上两个 reader 的约束），治理方式是 codegen 字节同步而非 `$ref` 引用。两种范式处理不同层面的问题，不冲突：

- CAS：同一 contractsRoot 内，`$ref` mixin → 物理单份（Hard）
- Error envelope：跨 contractsRoot，codegen mirror → 字节恒等 3 份（Medium）

## AI-robust 评级

### Funnel 双向锁

| 方向 | 形态 | 评级 |
|------|------|------|
| 上游（禁止外部写副本） | A1 reverse-enum archtest：全量扫 repo，未声明副本即 CI 红；JSON 文件无 Go 类型系统阻拦，最高只能到 archtest | **Medium** |
| 下游（`Headerless` 逃生口限制） | A2 caller-allowlist archtest：`WriteOptions{Headerless: true}` 复合字面量只允许在 `sharedschema` 包，类型信息确认，无灰区形态 | **Medium** |

整体评级：**Medium + Medium**（composite Medium）。两格均开 gh issue `#954` 跟踪 Hard 化路径。

### 为何不能评 Hard

本 funnel 形态落入 ai-robust.md §「codegen funnel + golden」范本，但 Hard 的前提是「regenerate-and-diff 字节级锁 + header 物理锚点」。JSON 文件无 `// Code generated` 前缀物理锚点（header 锚点），`governance.IsGoCellGenerated` 无法验证 mirror 身份。没有 header 锚点，上游（"外部写副本"）只能靠 archtest 事后检测（Medium）；下游（`Headerless` 选项）因 `WriteOptions.Headerless` 是导出字段无法 seal，也只能靠 caller-allowlist archtest（Medium）。

本 funnel**不在 ai-robust.md 的 Hard 范本目录新增条目**——它落入现有「codegen funnel + golden」范本的弱化变体，符号清单 / archtest ID 活在 `tools/archtest/shared_schema_mirror_test.go` 的 package godoc。

Hard 化方向（gh issue `#954` 跟踪）：
1. 上游：引入 codegen generate-time 自检，在 `gocell generate shared-schema` 执行后立即 `gocell verify codegen-shared-schema` 并 fail-fast；或把 mirror 文件置入 `generated/` 子目录（`governance.IsGoCellGenerated` 只检 header，子目录不解决）。
2. 下游：将 `Headerless` 从 `WriteOptions` 导出字段改为 unexported + 私有构造函数，使包外无法构造带 `Headerless=true` 的 `WriteOptions`，Go 类型系统阻拦（Hard）。

## Out of scope

- **消除 mirror**：两个 reader 的 allowlist 结构决定了物理副本是必需的，不存在通过消除副本来升 Hard 的路径；Hard 化只能走「reader allowlist 重构允许跨 root `$ref`」，成本极高，故意不取。
- **manifest 化 `hack/verify-schema-policy.sh` 全部 strict 行**：该脚本目前单列若干 strict 校验目标，其中 error envelope mirror 的 strict 性现由字节恒等 canonical 传递继承（见本 ADR §Consequences）；将脚本全部 strict 目标 manifest 化（结构化声明，archtest 守护）作为 backlog 追踪（issue 占位 `#955`）。
- **synth fixtures 分叉**：`tools/codegen/contractgen/testdata/synth/` 下有 3 份故意手工内容发散的 `error-response-v1.schema.json`，是 contractgen 行为测试用的 fixture——它们是有意不对齐 canonical 的 carve-out。A1 reverse-enum 用 `ModuleScope` 扫描（scanner 拒绝 `ModuleScope + IncludeTestdata`），`testdata/` 树天然排除在 A1 扫描之外，synth fixtures 与 `tests/contracttest/testdata/` 的声明 mirror 都不在 A1 扫描范围；后者的字节恒等由 `sharedschema.Verify`（verify gate）守护。

## Consequences

### 取代关系

- **删除** `TestSharedErrorSchema_CopiesInSync`（bytes.Equal 测试）：功能由 `gocell verify codegen-shared-schema`（in-process 字节 diff）取代，且后者比前者更严格——verify gate 在 CI 作为显式步骤强制运行，不只是测试包内的 t.Run。
- **`hack/verify-schema-policy.sh`**：不再需要单列 example mirror 的 strict 行；mirror 的 strict 性由「字节恒等 canonical」经 codegen funnel 传递继承。只需校验 `contracts/shared/errors/error-response-v1.schema.json`（canonical 源），mirror 与其字节恒等，strict 传递成立。
- **ADR `202605031600-adr-v1-schema-evolution.md` §5**：该节将 2 个 example mirror 列为独立 strict enforcement target，本 ADR 完成后该表述过时（见 §5 amendment）。

### 正向效果

- canonical 是唯一手写来源，`make generate` 后 3 个 mirror 自动对齐，AI 单独修改副本在下次 CI verify gate 时被发现。
- reverse-enum archtest 让「新增第 4 个副本」在 CI 立即可见，无需人工巡查。
- `Headerless` 逃生口被 caller-allowlist 锁住，AI 无法在其他 codegen 路径中悄悄重用该选项。

### 负向效果

- `Headerless` 字段是导出字段，上游不能完全 seal（Medium，见 §AI-robust 评级）。
- JSON mirror 无 generated header，`governance.IsGoCellGenerated` 无法区分"由 codegen 管理的 mirror"与"偶然同名的手工文件"，依赖 A1 archtest 补偿。

## Threat Model

| 风险 | 评估 | 缓解 |
|------|------|------|
| AI 直接编辑某 mirror 副本，绕过 canonical | 低 | A1 reverse-enum archtest 全量扫 repo，但只检测"副本存在"而非"内容对齐"——内容对齐由 `gocell verify codegen-shared-schema` verify gate 守护（CI 强制） |
| 新增第 4 个 mirror 副本未进 `sharedschema.Mirrors` 声明 | 低 | A1 archtest：未声明副本即 CI 红（reverse-enum 无枚举漏洞） |
| `Headerless: true` 被其他包滥用绕过 generated header 门 | 低 | A2 archtest：caller-allowlist 类型感知扫描，composite literal 包外即 CI 红 |
| verify gate 被跳过（CI 步骤被删除） | 低 | `tools/archtest/ci_pinning_test.go` 的 `codegenStepNames` 常量集锁 verify 步骤名（blind-spot ③），步骤被删即 archtest CI 红 |
| reader allowlist 升级后（Hard 化）引入 symlink 逃逸 | 低（当前不适用） | 当前 reader allowlist 结构决定必须保持物理副本；Hard 化时需同步审查 allowlist 逻辑 |
